### Task Q1: The TCP engine (audit C1, C2, I1, I2, the flaky 10 MB test)

**Files (read first):** `feature/lens/src/main/kotlin/$PKG/lens/core/{TcpFlow,FlowTable,Forwarder,PacketWriter}.kt`; tests `feature/lens/src/test/kotlin/$PKG/lens/core/{ForwarderTcpTest,TcpClientSim,FakeTun}.kt` (ADD, change nothing that exists unless named).

- [ ] **Step 1: Write the failing tests** (each must fail on `5094b22`; quote it):
  * **C1, end-of-stream spin.** The local server sends 1 MiB and closes. Assert: the forwarder sends **exactly one** FIN toward the app for that flow (count FIN packets in `FakeTun`), the `OP_READ` interest of the server socket is cleared after EOF (expose an `internal` counter `selectorWakeups` per flow or in total and assert it stays under 200 for the whole exchange, where the unfixed code reaches tens of thousands), `onServerEof` effects happen once, and 2 seconds after both sides closed the forwarder's CPU use is idle (the counter does not grow). Same for a client that closes first, for a server RST, and for simultaneous close.
  * **C2, FIN must not acknowledge unrelayed data.** The client uploads 16 MiB and sends its FIN immediately after the last data segment; the server (slow reader: reads 64 KiB then sleeps via a latch-controlled barrier, not wall time) must receive **all 16 MiB, byte-identical (SHA-256)**; the FIN is acknowledged only after every byte before it has been written to the server socket; a FIN with a sequence number beyond `rcvNext` (data missing before it) is not acknowledged and not processed until the gap is filled (out-of-order data/FIN is held or dropped with a re-ACK, never accepted early).
  * **I1, the app's window.** The client advertises a window of 4096 bytes: assert the forwarder never has more than 4096 unacknowledged bytes in flight toward the app at any moment (check the sequence arithmetic on every packet it writes); when the client's window is 0 the forwarder pauses the server socket reads (assert that no data packets are written while it is 0) and resumes when the window reopens; an app that stops reading for 60 simulated seconds does **not** receive an RST before the RTO/retry budget of the design (persist/zero-window probe: send a 1-byte probe every RTO while the window is 0 and the buffer is non-empty; keep the flow alive up to the idle timeout).
  * **I2, advertised window and uploads.** The advertised window equals the free space of the per-flow upload buffer (capped 65535, no scaling; 0 when full) and reopens with a window update when space frees up (assert a pure-ACK window update is sent); a 16 MiB upload through a slow server completes without any segment being dropped by the forwarder (counter `droppedSegments == 0`), and the transfer time is not dominated by retransmission timeouts (assert retransmissions seen by the client stay under 1% of segments).
  * **Flaky test.** Find the cause of `transfer_10mb_byte_identical` failing 2 of 5 times (`expected 10485760 but was 6234080` on the unmodified `5094b22`; it is very likely C1/C2 themselves) and show in the report that after the fixes the class passes **20 consecutive runs** (`./gradlew :feature:lens:testDebugUnitTest --tests "*ForwarderTcpTest" --rerun-tasks` x20 in a loop; quote the loop and the 20 results).
- [ ] **Step 2: Run to verify they fail** on the unfixed code (quote each failure).
- [ ] **Step 3: Implement the minimum that makes them pass.** At server EOF: clear `OP_READ`, emit the FIN once (state machine: ESTABLISHED to FIN_WAIT after the FIN is sent; do not re-enable read), keep only the interest ops the current state needs (write interest only while the upload buffer has data; read interest only while the downlink in-flight budget has room); never add a segment to the retransmission list without advancing exactly once. Process the client FIN strictly in sequence. Track `sndWnd` (the app's last advertised window, scaled by 1 since we do not negotiate scaling) and limit in-flight bytes to `min(sndWnd, 256 KiB)`; advertise `rcvWnd = capacity - buffered`; send a window-update ACK when `rcvWnd` grows from below one MSS to at least one MSS or doubles; zero-window probe as above. Remove any code path that drops client segments to throttle.

### Task Q2: Names, UDP, ownership, lifecycle and allocations (audit I3 to I8, protect)

**Files (read first):** `…/lens/core/{TcpFlow,UdpFlow,FlowTable,Forwarder,PacketWriter}.kt`, `SniParser.kt`; tests next to them (ADD).

- [ ] **Step 1: Write the failing tests** (each fails on `5094b22`; quote it):
  * **SNI over the first TLS record.** `TcpFlow` buffers the first client bytes (at most 16 KiB and only until the first TLS record is complete or 3 segments or 1 second of simulated time) and calls `SniParser.serverName` on the reassembled record. Test: a ClientHello of about 1.8 KB split across two and three segments (and with the second segment arriving first, out of order) reports the name once; a non-TLS first record (HTTP) reports nothing and stops buffering; the buffered bytes are still forwarded unchanged and in order (SHA-256 of the stream at the server).
  * **UDP large replies.** A UDP reply of 1,500, 4,000 and 60,000 bytes from the server: the receive buffer is 65,535 bytes; replies that do not fit in one TUN packet (`mtu - 28`/`mtu - 48`) are dropped and counted (`oversizedDatagrams`), the flow stays alive and the next normal reply is delivered (unfixed code kills the flow at 1,572 bytes).
  * **UDP parsed as DNS only on port 53.** A UDP flow to port 5353 or 8000 carrying a valid DNS-looking payload does NOT call `onDns`; port 53 replies do.
  * **Owner cache.** The UID cache is bounded (at most 4,096 entries, least recently used out) and an entry is removed when its flow closes; 100,000 short flows keep the cache size (an `internal` accessor) under the bound.
  * **`onFlowClosed` exactly once** for every flow in every close path (normal close, RST, eviction, idle timeout, `stop()`): a recording listener asserts each opened flow id is closed once and never twice.
  * **`protect()` failing.** A `SocketProtector` returning `false`: the flow is closed with an RST toward the app, **no connect is attempted** (assert the socket is never connected: use a counting channel factory), the counter `protectFailures` increments, and the forwarder keeps running. A throwing `protect()` behaves the same.
  * **Allocations.** Using `com.sun.management.ThreadMXBean.getThreadAllocatedBytes` on the network and TUN-reader threads (test-only, skipped with `Assume` if unavailable), relaying 50 MiB through an echo server allocates **at most 2x the payload** in total on those threads (the unfixed code allocates a 32 KiB buffer per read and per segment); implement with a small direct `ByteBuffer` pool and by building outgoing packets in place.
- [ ] **Step 2: Run to verify they fail**, **Step 3: implement**, **Step 4: pass five times in a row + gate**.
- [ ] **Step 5: Commit** `fix(lens): read names from the whole first TLS record, keep UDP flows alive, bound the owner cache and refuse to connect without protect()`.
